Professional Growth

Preparing for a Career in Computer Science

The following assessment reflects on the knowledge and skills I have developed thoughout the Computer Science Program.

Growth, Goals, and Professional Values

Completing the Computer Science program has helped me develop from a student learning individual programming concepts into a developer capable of developing complex software systems. Throughout the program, I learned how to produce successful software that not only will produce the correct output, but it will also be maintainable, efficient, and secure.

My coursework strengthened my ability to analyze requirements and decompose complex problems, as well as explaining the reasoning behind technical decisions. Developing this ePortfolio allowed me to bring those skills together. Revisiting earlier projects made it possible to identify limitations that I did not recognize when the projects we originally created. Enhancing that work demonstrates both my technical growth and my ability to critically evaluate my own work.

Collaboration in a Team Environment

Computer science is rarely an isolated activity. Effective solutions depend on developers being able to exchange ideas and work together to solve problems. My work over the course of the program has helped improve my collaboration ability by working with my peers and collaborating durring discussion posts and various assignments.

Durring the Software Development Lifecycle course, we worked as a SCRUM team to collaborate on a project. This enforfced good communication via the SCRUM stand-up meetings and other team communication that is required when working on a SCRUM team.

This experience showed me the importance of creating a enviornment in which feedback can improve the solution rather than being treated as criticism. As a professional, I will use code reviews and documentation to make decisions visible and help teams evaluate trade-offs together.

Communicating with Stakeholders

My experience as an instructor has had a major influence on how I communicate technical information. In the classroom, I cannot assume that every student will understand a concept after hearing it explained one way. I have to pay attention to where confusion starts, and explain it in a way that is easier to understand based on the needs of the person I am speaking with. That same approach applies to software development. A technical explanation may be useful to another developer, but a stakeholder may need the information presented in a different way.

Teaching has also shown me the importance of feedback. It is not enough for me to deliver information and assumer that it was understood. I need some way to check for understanding and use that repsonse to decide what should happen next. This idea directly influenced my Exit Ticket application. I created a Jaca client-server program that allows an instructor to porovide an exit-ticket question and allows users to connect and submit their responses. The question and responses are then saved locally for review.

This ePortfolio is another exercise in communicating to different audiences. The source code provides technical evidence, but the code alone does not explain why I made a particular choice or what I learned from it. The code review and project narratives allow me to explain my thought process for those projects.

Technical Experience

Data Structures, Algorithms, and Artificial Intelligence

My coursework has helped me become more deliberate about the way I solve programming problems. Earlier in the program, I was often focused on getting a program to work. As I gained more experience, I began paying closer attention to why a solution works, how it behaves with different inputs, and what happens as the amount of data grows.

In CS 370, I worked on a treasure-hunt project in which an intelligent pirate agent learned to navigate a maze using deep Q-learning. The project required the agent to balance exploration with exploitation, retain previous experiences, and improve its decisions through repeated training. Reaching a high win rate was only part of the evaluation. I also had to verify that the trained agent could reach the goal from every valid starting position.

That project reinforced an important lesson: a successful result does not automatically prove that an algorithm is reliable. The result has to be tested under more than one condition. I carried that lesson into my capstone work by testing the AVL tree with sorted, reverse-sorted, and shuffled course data rather than evaluating it with only one convenient input.

Software Engineering

My software projects have ranged from classroom-focused applications to mobile, networking, graphics, and embedded systems. Working across those areas has made me more comfortable entering an unfamiliar project, identifying the responsibilities of each component, and troubleshooting the connections between them.

The Exit Ticket application gave me experience building separate Java client and server programs around a classroom workflow. My Android inventory application required me to coordinate user interfaces, application logic, permissions, and local storage. I have also worked on projects involving OpenGL graphics, an embedded thermostat, and a digital toothbrush timer that uses an Arduino Nano, LED matrices, and a gyroscopic sensor.

These projects did not all present the same kind of challenge. Some required me to organize a larger amount of code, while others required me to work through communication between software and hardware. Taken together, they taught me to divide a problem into smaller responsibilities and test each part before assuming that the complete system will behave correctly.

Database Development

My database experience includes both relational and document-based databases. One project involved developing a reusable Python module for MongoDB CRUD operations. Instead of tying each operation to one specific screen or use case, I organized the module so that its create, read, update, and delete functionality could be connected to different MongoDB collections.

That project gave me experience thinking about the boundary between an application and its stored data. The calling code should not need to recreate database logic every time it performs a common operation. At the same time, the database layer needs to validate requests, return useful results, and handle unsuccessful operations clearly.

My Android inventory project added a different perspective by using SQLite and related tables on a mobile device. Returning to that project during the capstone made weaknesses in the original schema easier to recognize, including missing ownership relationships, limited constraints, and destructive database upgrades. The experience showed me that database design is not finished when data can be saved. I also have to consider who should be able to access it, how its integrity will be maintained, and how the structure can change without losing existing records.

Security

My work in CS 305 and CS 405 changed the way I look at software requirements. Security cannot be treated as a final check that happens after the rest of the program is finished. Decisions involving input validation, credentials, permissions, dependencies, stored data, and error handling all affect the security of a system.

This is also relevant to my experience as an instructor. A classroom application may collect student responses or other information that should not be exposed to every user. Even a small application needs clear decisions about what is collected, where it is stored, and who is allowed to retrieve it. Thinking through those questions has helped me connect secure-coding practices to situations outside of a security assignment.

When I returned to the Android inventory application for the capstone, I found that passwords were stored directly and that authentication did not establish ownership of inventory records. Recognizing the difference between confirming a user's identity and confirming what that user is allowed to access was an important part of the review. My planned changes address both concerns through password hashing, individual record ownership, authorization checks, database constraints, and safer migration behavior.
